# Security Specification & Threat Model (TDD)
## OST ERP - PostgreSQL Multi-Tenant & RBAC Hardening

### 1. Data Invariants & Zero-Trust Constraints

1. **Self-Promotion Block (Identity Integrity)**:
   - A standard user (e.g., Caixa, Vendedor) is forbidden from changing their own `role` or `status` to gain unauthorized administrative privileges.
   
2. **Account Blocking (User State Lockdown)**:
   - Users with an `status` value of `"INACTIVE"` or `"SUSPENDED"` must be immediately denied all read and write operations across all tenant entities.

3. **Audit Log Immortality (Audit Log Invariance)**:
   - Security audit logs stored in the `auditlogs` table are strictly write-once, append-only.
   - Updates and deletions of logs are strictly forbidden for all roles, including administrators.

4. **Timestamp Integrity (Temporal Safety)**:
   - The fields `created_at` and `timestamp` must be generated by authoritative server timestamps upon record creation.
   - The field `updated_at` must always be updated server-side.

5. **Entity ID Hardening (Tenant Isolation)**:
   - All operations are strictly scoped by `tenant_id` resolved from the validated authentication token, preventing cross-tenant leakage.

6. **PII Lockdown**:
   - Access to sensitive employee credentials (PIN, salary) is restricted to authenticated managers or administrators.

---

### 2. Malicious Payloads & Defenses
All threat vectors are rejected with `401 Unauthorized`, `403 Forbidden`, or validation errors (`400 Bad Request`).

#### Vector 1: Privilege Escalation on Profile Creation
- **Attempt**: A newly registering user tries to self-assign the `"ADMIN"` role.
- *Defense*: Server-side registration and authentication guards assign the default role based on verified tenant configuration.

#### Vector 2: Self-Promotion via Profile Update
- **Attempt**: Standard user tries to change their `role` from `"CASHIER"` to `"ADMIN"`.
- *Defense*: Non-admins are forbidden by `requireAdmin` middleware and database RLS.

#### Vector 3: Cross-Tenant Data Access
- **Attempt**: User with Tenant A credentials attempts to query or mutate records of Tenant B.
- *Defense*: Server endpoints enforce `user.tenantId` resolution and reject mismatched query predicates.

#### Vector 4: Erasing Audit Trails
- **Attempt**: Malicious actor attempts to delete an audit log.
- *Defense*: Deletion on `auditlogs` is prohibited in both API routes and database constraints.
